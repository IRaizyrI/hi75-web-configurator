# USB identification and descriptor evidence

## Current state

A metadata-only Windows inventory observed a `258A:010C` candidate with
vendor usage page `0xFF00`. USBPcap capture `003` also contains the device,
configuration, interface, HID-class, and endpoint descriptor bytes for the
device address subsequently used by the official app's `0x82` identity exchange.
This ties the captured descriptors to that app session; exact physical revision
is still unverified. The saved firmware image contains two candidate raw HID
**report** descriptors whose lengths and report sizes agree with the captured
configuration descriptor, Windows capability inventory, and browser-visible
WebHID collection layout recorded below. Their raw bytes have not been
obtained by a live `GET_DESCRIPTOR` request; WebHID exposes a parsed layout.

## Raw USB descriptors from official-app startup capture

Source: `captures/003_idle_startup/traffic.pcapng` (SHA-256
`21e86edb7cdc81076933345636e7985c4c28bb9bbe7f1378f64087f0600ed69f`),
frames 1–4, bus 2 / device address 5. The exact payloads are retained in
`captures/003_idle_startup/derived/control-transfers.json`. Capture `004`
repeats the same descriptor bytes before the lighting traffic. These are raw

HID capability metadata.

| 2 | Device, 18 bytes | `12 01 00 02 00 00 00 08 8A 25 0C 01 00 05 01 02 00 01` | `43cdac91e16ef71aa12c23e6d69cd136d12fed9d4351b1676d730901f90bc8f6` |

Decoded from those bytes: `bcdUSB=0x0200`, VID:PID `258A:010C`,
`bcdDevice=0x0500`, device class/subclass/protocol `0/0/0`, EP0 maximum
packet size 8, manufacturer string index 1, product string index 2, serial
string index **0**, and one configuration. The configuration advertises two
interfaces and bus-powered `bMaxPower=250` (500 mA in USB 2.0 units).

| Interface | Class / subclass / protocol | HID report descriptor length advertised | Interrupt IN endpoint | Packet size / interval |
| --- | --- | --- | --- | --- |
| 0 | `03 / 01 / 01` (HID boot keyboard) | `0x0043` (67 bytes) | `0x81` | 8 bytes / 1 ms |
| 1 | `03 / 00 / 00` (HID) | `0x00F0` (240 bytes) | `0x82` | 16 bytes / 1 ms |

The HID-class descriptors give only the **advertised lengths** of the two
report descriptors. Their 67- and 240-byte contents were not in the USB
capture, but were recovered from the preserved image as described below. The
interface-1 endpoint's 16-byte interrupt packet size does not limit the
520-byte feature reports sent through endpoint-zero control transfers. The
serial-string index `0` says this captured device descriptor advertises no
USB serial string; the earlier Windows HID getter's error 87 remains recorded
as its separate observation.

## HID report descriptors recovered from the saved firmware image

The preserved 61,440-byte application image (SHA-256
`31ee5b474b06b5bd26f32e15e379ce8c3251913b57dfebc3194a7c4dbdcc7ad0`)
contains **exact copies** of captured device-descriptor frame 2 at offset
`0x54E5` and configuration-descriptor frame 4 at `0x54F7`; each whole
captured descriptor occurs there only once. Immediately before the device
descriptor are contiguous, structurally valid HID report descriptors with
the advertised lengths: interface 0 at `0x53B2–0x53F4` (67 bytes, SHA-256
`a793c0d945b1047f33e64d404208e5e69fbe5494dc438fc22552d91af3fa396c`)
and interface 1 at `0x53F5–0x54E4` (240 bytes, SHA-256
`b67963b7e7759ee51e7766b2c1af46b81577bdf09f10634fa6839ca4a51beb46`).
The full hex and parsed items are in
[`analysis/firmware-usb-descriptors.json`](../analysis/firmware-usb-descriptors.json),
generated by the read-only
[`extract_firmware_usb_descriptors.py`](../tools/software-inspect/extract_firmware_usb_descriptors.py).
This is strong **firmware-image evidence** for the report layout, not a live
raw report-descriptor capture from the currently attached unit.

| Interface / report ID | Top-level usage page / usage | Declared Input bytes | Declared Output bytes | Declared Feature bytes |
| --- | --- | ---: | ---: | ---: |
| 0 / none | `0001 / 0006` | 8 | 1 | — |
| 1 / 1 | `0001 / 0080` | 2 | — | — |
| 1 / 2 | `000C / 0001` | 3 | — | — |
| 1 / 3 | `FF00 / 0001` | 4 | — | — |
| 1 / 4 | `0001 / 0006` | 16 | — | — |
| 1 / 5 | `FF00 / 0001` | — | — | 6 |
| 1 / 6 | `FF00 / 0001` | 8 | — | **520** |
| 1 / 7 | `0001 / 0002` | 8 | — | — |

Interface 1's vendor collection for report ID 6 declares an eight-bit
`Report Size` and `Report Count=519` for Feature data: **519 payload bytes
plus its one-byte report ID = 520 bytes**. This independently corroborates
the Windows 520-byte capability and official app's 520-byte `HidD_SetFeature`
and `HidD_GetFeature` buffers. The browser snapshot below independently shows
519 payload bytes for this report, without exercising report I/O. This does
not make a proprietary command safe to replay.
Interface 0 uses no report ID; its 8-byte Input and 1-byte Output are descriptor
report lengths, whereas the Windows HID API reserves a leading report-ID slot
and reports 9/2-byte buffers.

Capture `003` also contains eight actual eight-byte interrupt-IN reports on
interface-1 endpoint `0x82`: each is `06 0A 05 64 01 00 00 00` during an
official-app identity exchange. This confirms an on-wire input report ID `6`
with seven data bytes for this session, consistent with both the saved-image
descriptor and WebHID snapshot. The temporal and firmware-flag evidence is
detailed in [`protocol.md`](protocol.md#offline-audit-of-read-shaped-transfers).

## Windows inventory procedure

Use [`tools/hid-inspect/README.md`](../tools/hid-inspect/README.md) for the complete
procedure, commands, output schema, API references, and USBView supplement.
From `hi75-web`, a pasteable candidate snapshot is:

```powershell
.\tools\hid-inspect\Inspect-Hid.ps1 -VendorId 0x258A -ProductId 0x010C
```

Omit both filters for the initial complete inventory. The tool queries metadata
only and sends no output/feature reports; it does not read feature/input reports
or current keyboard configuration. Nulls and query errors must remain visible.

Before interpreting a snapshot as Hi75 evidence, record the physical model and
associate its USB nodes with the unit. See the optional unplug/replug comparison
in the tool guide. Do not use VID/PID, generic strings, or buffer sizes alone to
approve a revision or enable writes.

## Next physical-device information

Collect without flashing firmware or sending exploratory HID packets:

1. **Physical identity:** model label, wired variant, purchase/model revision if
   known, and photos of external labels. Do not disassemble just for this step.
   Keep serial numbers private when sharing publicly.
2. **Environment:** OS/version, USB connection arrangement (direct or hub), and
   the official application name/version and download source. Record a SHA-256
   of its installer/executable if available. Record firmware version only if
   already displayed by the application; do not update firmware to obtain it.
3. **Full device descriptor:** VID, PID, `bcdDevice`, `bcdUSB`, manufacturer,
   product and serial string availability, and configuration count.
4. **All configuration/interface/endpoint descriptors:** interface numbers,
   alternate settings, classes/subclasses/protocols, endpoint addresses,
   transfer types, maximum packet sizes, and polling intervals. Include every
   HID interface, not just the suspected vendor interface.
5. **Raw HID report descriptors for each HID interface:** retain exact bytes and
   a decoded export, including usage pages/usages, collections, report IDs,
   and Input/Output/Feature report sizes and counts. Distinguish endpoint packet
   sizes from full report lengths and state whether lengths include report IDs.
6. **Official-app USB captures:** baseline startup/idle followed by controlled
   lighting changes, as described in `reversing.md`.

Use descriptor exports from a USB inspection tool or captured enumeration where
available. Screenshots can supplement but should not replace raw descriptor
bytes. Record the inspection tool/version and collection method.

## Future fingerprint policy

VID/PID alone must never enable writes. Build an evidence-backed profile from
multiple attributes, including descriptor bytes/hash, interface/collection
structure, report definitions, and verified model/revision evidence. Product
strings and physical appearance are supporting evidence, not sufficient gates.

If traffic later establishes a safe device-info request, its verified response
may add fingerprint evidence. No such request is known yet. Unknown or mismatched
revisions default to read-only, with only independently verified non-mutating
operations permitted. The matching algorithm and accepted profiles remain to be
designed after descriptors and traffic are available.
